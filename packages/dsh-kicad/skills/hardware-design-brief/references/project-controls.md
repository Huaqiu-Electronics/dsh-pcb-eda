# 文档一致性与验证检查

本指南用于模型内部自检，不是审批流程。默认不生成独立决策日志、决策编号或签核表。保持方案的技术深度，减少重复记录和对用户的确认请求。

## 信息放在对应位置

- 产品目标、来源和验收条件放在 PRD；选型、电路取舍、参数依据和预算放在方案的对应章节；实测证据引用实际试验记录。不要把同一结论再抄入决策文件。
- 假设直接注明在受影响参数或方案旁，足以解释适用条件即可。关键未决项在相关文档末尾简短列“缺什么—影响哪部分—下一步怎么解决”；无实质未决项时不建空表。
- 需求/板号/接口编号沿用已有规则，保留需求→板卡/电路→验证的对应关系，不再额外建立 `D-001` 决策条目。
- 每份文档保留版本/日期和输入依据。用来源与证据说明用户要求、工程建议、假设、计划和实测结果，不为每项添加等待用户签核的状态。

用户明确要求独立决策日志，或已提供的团队规范明确要求时再使用；不因“企业项目”“受监管产品”或旧日志存在而自动增加审批。已有日志保留历史和必要引用，新内容默认写回对应文档，不擅自删除旧文件或要求用户批准迁移。

## 什么时候才需要问用户

先看已有输入、优先级和授权能否回答，再查资料或计算；只有关键取舍确实无法代决时提问。

| 情况 | 处理方式 |
| --- | --- |
| 用户已给过信息、已选择或已授权模型决定 | 直接沿用；无新矛盾不再次询问 |
| 常规选型、引脚/外围计算、文档组织、资料可查的事实 | 自行核实并决定推荐基线，说明依据，继续实施方案 |
| 可逆、影响有限且可作合理假设的缺口 | 明示假设后继续，不要求每条都被确认 |
| 待查手册、供应商资料或待实测项目 | 作为工程待办，记录取得证据的方法；用户回复“确认”不能替代证据 |
| 核心需求冲突或缺少关键外部条件，且无既定取舍依据 | 尽量合并提问，给推荐及影响；只限制依赖该答案的部分，其他工作继续 |
| 用户明确要求阶段审批 | 按用户规定的节点暂停，不追加其他审批节点 |

未回复不代表批准；也不意味着已经授权的独立工作都要停下。涉及供电、隔离或其他关键电气边界而无可靠依据时，不用随意默认值掩盖缺口，相关部分保持有范围限制的草案。

## 内部检查与验证计划

编写过程中自检，不逐阶段向用户申请“通过”：

- MRD 能说明目标用户/任务、范围、组成及成功条件；PRD 能给出可验收要求、来源、板级分配和接口边界。
- 每项必须需求有具体板卡、器件/电路或接口的实现归属，以及验证方法；没有 MRD 时直接追溯用户输入或已有规格。
- 硬件方案按 [solution-deliverable.md](solution-deliverable.md) 检查主选型号/封装、电路/外围、关键引脚、板间连接、预算和 PCB 约束。技术内容不完整不能以“减少流程”为由宣布完成。
- 验证计划关联需求/风险，给方法与工况、通过条件、执行阶段和证据状态；需要时补资源/责任。覆盖适用的方案分析、原理图/PCB 审查、样机测试和后续验证，未执行的活动不写“通过”。
- 面向实际使用场景保留演示或使用验证，避免仅满足局部技术指标而不能解决原问题。

交付时简短说明哪些板/模块已具备原理图展开条件、哪些仍受关键缺口限制即可。不强制输出三级阶段结论或阶段签核表，不以“请确认后继续下一阶段”收尾。只有缺少必要设计输入才限制相应工程交接；“未获得用户逐项批准”本身不是技术缺口。

## 更新时保留必要依据

直接修改授权范围内的主文档，简述会影响实现的变化及理由；一般修订无需额外日志、旧值新值表或审批。保留稳定需求/板号/接口编号，不伪造历史或覆盖仍需引用的证据。

同步检查受影响的需求、分板/实例、器件/引脚、电路、板间接口两端、预算与验证条件。不能核实的下游内容标为待复核；仅获授权修改单文件时列出其他受影响位置即可。旧实测结果不自动成为新条件下的通过证据。
