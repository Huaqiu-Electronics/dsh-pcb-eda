# 硬件产品需求与设计输入

帮助工程师把市场需求逐步转成可验收的产品要求，再转成原理图和 PCB 设计输入。按用户实际请求生成其中一份或整套文档，不强制补齐未请求的阶段。

## 本技能与同包能力的配合

安装 `@huaqiu/dsh-kicad` 后，本技能随该插件一起可用，无需单独安装技能。

本技能是**知识型技能**：它不注册任何工具，只提供提问流程、文档结构和“已确认 / 有来源 / 建议 / 假设 / 待确认”的区分口径。同包内的 `kicad-ipc` 技能负责把本技能产出的设计输入落到实际 PCB 上，并提供一组 `kicad_pcb_*` 工具（新建走线、过孔、铜区、移动/旋转封装、删除选中对象等）。

两者的分工是：

| 阶段 | 归属 | 产出 |
| --- | --- | --- |
| 市场需求、产品要求、设计输入 | 本技能 | `docs/01-MRD.md`、`docs/02-hardware-PRD.md`、`docs/03-design-brief.md`、`docs/decisions.md` |
| 把设计输入落到 PCB（读取、修改、验证、保存） | `kicad-ipc` 技能 + `kicad_pcb_*` 工具 | 实际板卡改动 |

当讨论进入“具体要在板上做什么”时，参照 `kicad-ipc` 技能：任何改动前先用 `kicad_ipc_diagnose` 确认 KiCad 可连接，改动后重新读取受影响的状态确认，保存由 `save` 参数显式控制。

`references/` 下的三份指南按需读取（见下文），它们是本技能的一部分，不会自动全部加载。

## 文档位置与关系

把生成的项目文档放在**项目根目录的 `docs/`**，与本 skill 的 `references/` 分开。整套文档使用以下文件名；用户已有命名约定时沿用其约定，不另建重复文件。

```text
docs/
├─ 01-MRD.md                 市场需求：目标客户、场景、机会与商业边界
├─ 02-hardware-PRD.md        硬件产品需求：产品必须达到什么、如何验收
├─ 03-design-brief.md        原理图和 PCB 设计输入：如何落实已确认要求
└─ decisions.md              假设、未决问题、决策及变更依据
```

MRD 说明“谁需要、为何需要”；PRD 定义“产品必须达到什么”；design brief 将已确认的 PRD 要求转成可供原理图和 PCB 开工的约束与选择。使用稳定编号串联：MRD 为 `M-001`，PRD 为 `H-001`，PRD 标注来源的 MRD 编号，design brief 引用相关 PRD 编号。只给可追溯的需求编号，避免给普通叙述逐句编号。

## 对话与生成

1. 先阅读用户提供的背景和已有文档，确认项目根目录、目标交付物及已知约束。若项目位置明确，直接使用；不要重复询问已给出的信息。
2. 按影响决策的程度分批提问，每轮只问少量相关问题，允许部分回答或填写“暂不确定”。先解决会改变目标市场、产品范围、核心功能、供电、接口、尺寸、层数或成本的问题。
3. 区分**已确认**、**有来源的事实**、**建议**、**假设**和**待确认**。市场数据、竞品参数和器件能力若未核实，不写成事实；关键未知不能用臆测填满。遇到互相冲突的要求，指出冲突并请求取舍。
4. 生成用户要求的文档；若用户要求整套文档，按 MRD → PRD → design brief 的依赖关系编写，并在 `docs/decisions.md` 记录会影响后续设计的假设和未决事项。缺少上游文档时，也可先做下游草案，但应标注其市场或产品前提。
5. 检查各文档中数值、单位、状态和编号是否一致。下游文档不能把上游的假设或待确认事项升级为已批准要求。对更新过的要求，指出受影响的后续条目。

按当前任务读取对应指南，不必一次加载全部：

- 创建或更新 MRD：阅读 [references/mrd-guide.md](references/mrd-guide.md)。
- 创建或更新硬件 PRD：阅读 [references/hardware-prd-guide.md](references/hardware-prd-guide.md)。
- 创建或更新原理图与 PCB 设计输入：阅读 [references/design-brief-guide.md](references/design-brief-guide.md)。

用户只想讨论方向时先讨论；用户只要求一份文件时仅创建或修改该文件，必要的未决问题可直接列在该文件末尾。
