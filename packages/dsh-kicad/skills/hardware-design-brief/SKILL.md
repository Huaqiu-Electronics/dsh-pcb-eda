# 硬件产品需求与方案定义

帮助工程师回答“为何做、做到什么程度、选什么、怎样连接、如何验证”。默认终点是**完成可供原理图展开、并指导后续 PCB 的硬件实施方案**：后续工程师无需重新选择核心器件、设计主要接口或重新决定模块连接。方案完成不等于实测通过或生产放行。

## 先确定范围与深度

先读已有资料，识别产品/单板边界、当前阶段、目标产物、关键约束及项目目录。信息足够时直接工作；不要要求用户重新填写已有信息。

按项目风险、复杂度和协作需要裁剪，不按用户资历增加文档：

| 情况 | 使用方式 |
| --- | --- |
| Maker、学习验证、一次性工装、明确用途的小改版 | 精简管理文档：可将背景、需求与完整实施方案合成一份；选型、电路、连接和预算深度与企业项目相同，不要求市场规模或销量 |
| 新产品、商业化、小团队多人协作 | 标准：MRD、硬件 PRD、硬件方案；选型理由、假设、验证与风险在对应文档内说明 |
| 多 PCB /跨团队项目 | 按整机→单板→板间接口分解，给每块自研 PCB 独立的需求分配和实施方案；小项目可按章节拆分，复杂项目分文件 |
| 关键技术不确定、后果严重或受监管的产品 | 加深关键试验、接口和证据；有关键缺口时交付受限草案，不冒称方案完成 |
| 已有 PRD、仅审核/修改某份文档 | 从当前阶段进入；补必要前提和缺口，不倒推编造 MRD，不自动重做整套文档 |

精简的是管理开销，不是电路方案。Maker 采用现成模块时，要明确模块型号/版本、实际引脚、电源和互连，不能只写“用一个传感器模块”。对新手解释选择及连接方法，不把选型工作以问题清单推回给用户。

## 主流程与阶段边界

```mermaid
flowchart LR
    A[需求来源：市场 / 用户任务 / 已有产品] --> B[MRD 或精简立项说明]
    B --> C[产品需求与硬件 PRD]
    C --> D[硬件实施方案：分板 / 选型 / 电路 / 互连 / 预算]
    D --> E[原理图展开与 PCB 设计]
    D --> F[关键假设验证或概念原型]
    F --> C
    F --> D
    C --> B
```

MRD 回答谁需要、为何值得做；PRD 定义整机结果、验收及已有板级边界；硬件方案确定实现路线、核心器件、电路连接和板级分配。可行性分析可提前介入；新增分板决策反馈 PRD，不能把主流程当作不可回退的瀑布。

**完整方案必须同时有图、有选型、有电路、有连接、有预算**。至少有系统框图和电源树（简单项目可合图），每块自研 PCB 有板内模块连接与电路说明，多板还必须有板间互连表。采用采购模块时落实其外围和实际接口，不要求重设计模块内部电路。方案的章节和技术粒度统一参考 [交付结构与验收清单](references/solution-deliverable.md)，不因 Maker 身份降级成宏观简报。

本阶段要给出推荐封装、关键外围及参数依据、保护/驱动/复位/烧录方案、连接器与信号分配、布局布线约束。层数、板厚和外形应有已知约束或有依据的建议；涉及阻抗、隔离和散热时给设计目标。完整原理图绘制、全部位号/焊盘、最终叠层及布线、制造装配文件仍由后续落实。具体划分见 [阶段边界指南](references/stage-boundaries.md)。

## 最小文档集合

生成文件放在**项目根目录的 `docs/`**，不要放进 skill 的 `references/`。用户已有命名与目录时沿用；已有明确工作目录时直接使用，不专门询问保存位置。确实无法判断目标目录时再询问，内容编写可继续。

标准模式默认使用：

```text
docs/
├─ 01-MRD.md                 市场/立项依据、场景、成功目标与范围
├─ 02-hardware-PRD.md        整机/板级需求分配、接口边界、验收方法
└─ 03-design-brief.md        整机方案与单板实施方案，或多板方案索引
```

**默认不创建或维护独立的 `decision.md` / `decisions.md`，也不建立决策编号、签核或逐阶段确认流程。** 选型理由写在选型处，假设注明在相关参数旁，关键未决项集中在受影响文档末尾。只有用户明确要求独立决策日志，或已提供的团队规范明确要求时才使用。既有日志保留历史和必要引用，不因其存在自动恢复逐项确认或要求用户批准迁移。

保留 `03-design-brief.md` 文件名以兼容旧项目，标题与内容改为“硬件方案设计”。更新旧文件时保留仍有效的详细约束，并标注阶段归属，不擅自删除工程输入。

精简模式默认生成 `docs/project-brief.md`，以章节承载完整需求和实施方案；不以“简报”为由省略选型或电路。多板项目在 MRD 中识别已知产品组成，在 PRD 中分配整机/单板要求，在方案中明确每种 PCB 的稳定编号、数量、边界和互连，并逐板展开。通常增加 `docs/boards/B01-名称.md` 等单板文件和 `docs/interfaces/board-interconnects.md`；用户只要一个文件时改为独立板级章节和公共互连表。详见 [多 PCB 指南](references/multi-board-guide.md)。

非市场驱动项目不要求单独 MRD；用户仅请求一份文件时只交付该文件，把前提、板级分解、风险和待办内嵌。

不要以文件数量判断完整性。核心选型表和工程 BOM/成本估算是本阶段产物；用于投产的完整 BOM、EDA 文件、实测报告和生产装配包由后续形成。每项信息保持唯一维护位置并建立引用。

## 工作方式

1. **选择入口**：记录本次阶段、采用的文档深度和已有输入。审核时先报告缺陷及影响，再在授权范围修改；小改动只更新受影响项。
2. **仅询问真正需要用户判断的缺口**：先利用已有输入和可查资料。只有无法据此确定、无法用可接受假设继续，且会实质改变产品目标、硬约束或关键方案的问题才询问；尽量合并一次提出，附推荐及影响。普通选型、可计算参数、文档结构与下一阶段是否继续，由模型在授权范围内直接处理。新问题出现时再补问，不将问答轮数当作流程。
3. **主动完成工程决策**：对已有充分条件的模块核对资料、选定推荐基线、规划连接并计算参数，直接用于后续文档，不逐项请求批准。可逆且不影响核心要求的缺口使用明示假设继续；真正缺少的关键外部条件只限制相关部分。资料核实、计算或试验任务由相应工作解决，不转换成让用户逐条“确认”的问题。缺少关键证据时如实标明范围，不编造完成状态。
4. **建立证据**：分别标明用户确认、外部资料事实、工程推算、建议、假设和待确认。核对当期竞品、价格、器件能力/供货及适用标准时记录链接、资料版本或查询日期；无法查证时说明局限。目标、计算估计与实测结果分别记录。
5. **连续编写和自检**：请求整套文档时按 MRD → PRD → 方案连续完成，阶段检查由模型内部执行，不在每份文件结束时停下要求确认。缺上游文件时引用用户输入或已有规格；冲突若已有优先级或授权可据此处理，否则只对确实需要用户取舍的部分提问，其他工作继续。
6. **检查并交付**：按交付清单核对需求→板卡→器件/电路→接口→验证，检查封装/引脚、资源与存储容量、电源兼容、板间针脚、成本加总、图表一致性。报告可进入原理图的具体板卡/模块与阻塞范围。仅有框图、候选类别和待办清单不算完成硬件方案。

用户只想讨论时先讨论，不强制落盘。只要没有新的实质冲突，不重复确认用户已给出的信息或已授权的选择，也不以“请确认后再生成下一份文档”收尾。文档保留版本/日期、来源和实际证据状态；“未由用户签核”本身不阻塞编写、推荐选型或方案交接，不能据此新增审批。不得把工程建议冒充用户要求，或把未执行试验写成通过。用户明确要求阶段审批时才按其要求暂停。

## 按需读取

- MRD 或精简立项说明：[mrd-guide.md](references/mrd-guide.md)。
- 产品需求及硬件 PRD：[hardware-prd-guide.md](references/hardware-prd-guide.md)。
- 每次生成或审核完整硬件方案，读取 [design-brief-guide.md](references/design-brief-guide.md) 和 [solution-deliverable.md](references/solution-deliverable.md)。后者将用户提供案例的深度转成通用交付规范，并链接案例全文。
- 多 PCB 或产品组成尚需分板决策：[multi-board-guide.md](references/multi-board-guide.md)；MRD、PRD 和方案阶段均适用。
- 判断 PCB/装配细节是否属于当前阶段，或准备详细设计交接：[stage-boundaries.md](references/stage-boundaries.md)。
- 整套文档、审核及跨文档变更的内部一致性与验证检查：[project-controls.md](references/project-controls.md)，不据此增加审批流程。

只加载本次工作相关指南。单文件任务也应保留最小追溯：稳定的需求编号（MRD 为 `M-001`，PRD 为 `H-001`）、来源、验收依据、未决项；普通叙述无需逐句编号。
