# 规划 ③ — 传输优化（只规划，本轮不做）

> 现状：DSH 路由把**整份 `.kicad_pcb` 文本**发给浏览器（Jetson 板 81MB）。
> 本地 loopback 实测 0.13s / 642MB/s，但这是**本机**；跨机/远程 DSH、或十亿级文本时，
> 传输会重新变成瓶颈。而且 81MB 文本在浏览器里还要占内存 + 解析（~1.3s）。

## 目标

让浏览器**只拿到渲染需要的东西**，而不是整份 KiCad 源文件。

## 方案（按收益/成本排序）

### 方案 A（推荐，收益最大）：服务端解析 + 只传精简几何

host 半边已经会解析（`readStats` 里就 parse 了一次）。把解析结果里**渲染真正用到的字段**序列化后下发：

| 数据 | 现状（整份文本） | 精简后 |
|---|---|---|
| 焊盘 | 每个 `(pad …)` 几十行 s-expr | `{x,y,w,l,shape,net,top,bottom,th}` × 4862 |
| 走线 | 每段 s-expr | `{pts,w,layer}` × 22151 |
| 铜皮/过孔/器件/丝印/外框 | 同上 | 同上 |

Jetson 板估：81MB 文本 → **几 MB 二进制/紧凑 JSON**（gzip 后更小）。浏览器侧省掉解析（~1.3s）与 80MB 内存。

**代价**：需要一条新的内容类型/编码（建议 JSON + gzip，或简单自定义二进制），
`/pcb-viewer/api/file` 之外加 `/pcb-viewer/api/model?key=`；浏览器侧 `parseBoard` 走"已是模型"分支。
`BoardModel` 就是现成的契约，序列化几乎零成本。

### 方案 B（低成本先做）：传输层压缩

路由加 `content-encoding: gzip`（81MB 文本 → 约 5–8MB）。改动只有 host 几行 + 客户端 fetch 自动解压。
**但**：浏览器仍需解析全文（1.3s）与占内存，只解决传输。

### 方案 C：流式解析（收益有限，复杂）

边下边解析（`TextDecoderStream` + 增量 tokenizer）。能压低首字节到首图的时间，
但要重写 tokenizer 为可重入状态机，**不建议**。

## 建议路线

1. **先做 B**（半天内，风险极低）：gzip 传输，立刻改善远程场景
2. **再做 A**（真正的解法）：服务端出模型、客户端直接建场景；A 做完后 B 可保留（模型 JSON 也 gzip）
3. C 不做

## 验收基线（做之前先记录，便于对比）

| 指标 | 现状（Jetson 81MB，本机） |
|---|---|
| 路由传输 | 84.8MB / 0.13s（loopback） |
| 浏览器解析 + 建模 + 纹理 | ~1.5s |
| 首屏（2D/3D） | 2D ~6.2s / 3D ~6.0s 板相关增量（SwiftShader 软渲染，真 GPU 更低） |

## 风险与注意

- **不要把渲染搬到服务端**：本插件的价值是浏览器实时渲染（可交互、可拆解、可分享链接），
  服务端只出**数据**，不出图
- 模型 JSON 版本化：`BoardModel` 加字段时要有 `schemaVersion`，避免新旧 host/client 混跑出错
- 大板模型仍建议走**轻量模式**（缩略图 `textures:false`）——传输优化不替代这条路径
